## Goal

The uber JARs of `protobuf-setup-plugins` and `jvm-tool-plugins` (published as
`protobuf-setup-plugins[-all]` and `jvm-tool-plugins[-all]`) stop bundling the
Protobuf runtime. They declare it as a `runtime` dependency instead, so that
the Protobuf runtime resolved by a consumer wins on its build classpath.

## Context

Both JARs embedded unrelocated `protobuf-java`, `protobuf-java-util`, and
`protobuf-kotlin` classes — `RuntimeVersion` read `4.36.2` in `.426`. Each build
therefore pinned the runtime it was built with. In the dependency refresh wave
`cascade-refresh-a0cbbbf` (Protobuf `4.36.0 → 4.36.2`), consumers loading code
generated by `4.36.2` next to `.422`/`.425` failed with
`ProtobufRuntimeVersionException: … gencode 4.36.2, runtime 4.36.0`. `force(...)`
cannot help, because the copy is bytecode inside another artifact rather than
a dependency. The wave had to add `eachDependency` rules in `core-jvm` and
`jdbc-storage`, and `core-jvm-compiler` had to stop using the dogfooding JAR.

Relocation is not an option: the Protobuf runtime depends on the names of its
classes. Bundling is not required either. The JARs are uber JARs so that their
Spine-only dependencies need no Spine repository on the Plugin Portal, and
Protobuf is on Maven Central.

This repeats `unshade-intellij-platform-third-party` for a different library.
